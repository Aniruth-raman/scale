# BLE protocol evidence

Status: **candidate, code-derived; weight reported by the user to match the
scale. Body composition and other protocol families remain unverified.**

Confidence terms used here:

- **C** — confirmed in decompiled code (UUIDs, framing, field offsets, unit
  codes, control flow).
- **H** — hypothesis supported by code but with a semantic ambiguity.
- **U** — unverified on the physical scale.

No UUID, packet layout or scaling factor in this document was invented. If a
field was not found in code, it is marked unknown rather than guessed.

## 1. GATT profile

From `com/pingwang/bluetoothlib/config/BleConfig.java:21-24`:

| Role | UUID | Confidence |
|---|---|---|
| Service | `0000FFE0-0000-1000-8000-00805F9B34FB` | C |
| Write | `0000FFE1-0000-1000-8000-00805F9B34FB` | C |
| Notify | `0000FFE2-0000-1000-8000-00805F9B34FB` | C |
| Write + notify | `0000FFE3-0000-1000-8000-00805F9B34FB` | C |
| CCCD | `00002902-0000-1000-8000-00805F9B34FB` | C |

AILink subscribes to both `FFE3` and `FFE2` on connection
(`BleDevice.java:491-492`, `openAILinkNotify`). The exact characteristic
properties (write-with-response vs write-without-response, notify vs indicate)
must be read from the physical GATT table; the names above are what AILink
uses, not a substitute for discovery.

AILink's scan filters use the broadcast service UUIDs `FFE0` and `F0A0`
(`BleConfig.java:19-20`, feature activities). The replacement scans unfiltered
and lets the user select the device.

## 2. Frame formats

All frames use a start byte, length, payload, checksum and terminator.
The checksum is the low byte of the sum of every byte after the start byte and
before the checksum. Evidence: `AiLinkBleCheckUtil.java:38-78` for building,
`:80-156` for validation, `BleDevice.java:689-729` for dispatch.

### A6 (module/application command)

```text
offset 0: 0xA6
offset 1: payload length (N)
offset 2..N+1: payload
offset N+2: checksum (sum of bytes 1..N+1)
offset N+3: 0x6A
```

The A6 handshake is a special case: `A6 <N+1> <cmd 0x23/0x24> <16-byte key>
<checksum>` and has no `0x6A` terminator (`AiLinkBleCheckUtil.sendHandshakeFormat`).
The replacement does not implement the handshake.

### A7 (MCU command, carries scale data)

```text
offset 0: 0xA7
offset 1..2: CID, big-endian
offset 3: payload length (N)
offset 4..N+3: payload
offset N+4: checksum (sum of bytes 1..N+3)
offset N+5: 0x7A
```

`BleDevice.protocolNotifyData` extracts the CID from bytes 1-2 and passes the
payload to the scale decoder (`BleDevice.java:707-725`).

### Synthetic examples

| Frame | Hex | Meaning |
|---|---|---|
| A7 CID 86 stable | `A7 00 56 05 02 00 1B 58 20 F0 7A` | 70.00 kg, stable |
| A7 CID 86 complete | `A7 00 56 01 0A 61 7A` | measurement complete |
| A7 CID 50 live weight | `A7 00 32 06 01 01 00 1B 58 20 CD 7A` | 70.00 kg, live |
| A6 version probe | `A6 01 0E 0F 6A` | documented get-version request |

These frames are synthetic, generated by `tools/make_fixtures.py`. They do not
contain real measurements.

## 4. Weight-only scale (CID 86)

Source: `com/elinkthings/modulebleweightscale/ble/WeightScaleDevice.java:104-219`,
`WeightScaleConfig.java`, `BleMeasureDataViewModel.java`.

A7 payload layout for weight-bearing messages:

```text
byte 0: message type
byte 1..3: raw weight, 24-bit big-endian, unsigned
byte 4: high nibble = decimal places, low nibble = unit code
```

Message types:

| Type | Meaning | Action |
|---:|---|---|
| 1 | real-time/live weight | update live UI, do not save |
| 2 | stable weight | keep as candidate, do not save yet |
| 5 | infant-mode weight | display as infant reading; not auto-saved |
| 9 | BMI, 16-bit BE / 10 | body-composition metric `bmi` |
| 10 | measurement complete | save the preceding stable reading |
| 130 | unit result | diagnostic only |
| 255 | error code | show error, do not save |

Unit codes (`WeightScaleConfig`; `UnitUtil.weightUnitToString`):

| Code | Unit | Storage conversion |
|---:|---|---|
| 0 | kg | as-is |
| 1 | jin (`斤`) | × 0.5 kg (`UnitUtils.fgToKG`) |
| 4 | st:lb | raw value is pounds; × 0.45359237 kg |
| 6 | lb | × 0.45359237 kg |
| 2, 3, 5 | values used elsewhere in AILink | not observed in this scale; decoder rejects them |

Decimal places observed in code: 0, 1, 2, 3. The decoder rejects >3.

The weight is unsigned 24-bit. AILink's view model has a sign parameter but the
weight-scale callback passes 0; no negative weight packet was found.

## 4b. Four-electrode body-fat scale (CID 14/94/118)

Source: `cn/net/aicare/modulebodyfatscale/ble/BodyFatBleUtils.java:111-280`,
`BodyFatDataUtil.getWeightInt/getWeightPoint/getWeightUnit`.

The weight payload uses the CID 86 layout: byte 0 is the message type,
bytes 1-3 are the 24-bit big-endian weight, byte 4 is decimal/unit.

| Type | Meaning | Action |
|---:|---|---|
| 1 | testing/live weight | update live UI, do not save |
| 2 | weight result | keep as stable candidate |
| 18 | infant result | display as infant; not auto-saved |
| 10 | test finish | save the preceding stable result |
| 9 | body-fat data | **not decoded**; AILink's local algorithm fields are not guessed |
| 130 | unit result | diagnostic |
| 255 | error | show error |

The replacement supports weight for this family. Body-composition data is
omitted because the payload is tied to AILink's local Holtek calculation and
has not been verified; do not present it as transmitted scale data.

## 5. Eight-electrode scale (CID 19/50/82/104)

Source: `aicare/net/eightscale/ble/EightBodyFatBleDeviceData.java`.

Weight messages use the same 24-bit BE + decimal/unit nibble, but with one
state byte before the weight:

```text
byte 0: state (1 = weight)
byte 1: substate/state flag
byte 2..4: raw weight, 24-bit big-endian, unsigned
byte 5: high nibble = decimal places, low nibble = unit code
```

State handling used by the replacement:

| State | Meaning | Action |
|---:|---|---|
| 1 | weight notification | update live UI; not saved alone |
| 2 | analysis/status | diagnostic; substate 2 is an analysis failure |
| 3 | heart rate | diagnostic; not stored |
| 4 | temperature | diagnostic; not stored |
| 9 | body-composition metrics | merge into current measurement |
| 15 | measurement finished (CID 19/50) | save the most recent weight |
| 15 | dual-MCU ADC test complete (CID 82/104) | diagnostic only; not a measurement completion |
| 255 | error | show error; do not save |

State 9 body composition is decoded only for MCU CIDs 50 and 104; the app/dual
paths in AILink do not define that payload.

`getWeight`, `getDecimal` and `getUnit` are at
`EightBodyFatBleDeviceData.java:980-1034`. The unit table is the same as CID 86.

The eight-scale stream does not expose a separate stable flag. The completion
state 15 is the explicit save trigger, and the last weight notification in the
cycle is used. A completion with no recent weight (30 s) is ignored.

## 6. Body-composition metrics

The MCU sends state `9`, subtype `1..9`, with 16-bit big-endian fields
(`0xFFFF` is treated as 0). The single MCU path handles subtypes 1-4; the dual
MCU path handles 1-9 (`isMcu` vs `isDualMcu`). The field-to-UI mapping is in
`EightBodyFatScaleMainActivity.java:1109-1240`.

| Subtype | Fields (as stored by the replacement) | Evidence |
|---:|---|---|
| 1 | `bmi`, `bodyFatPercent`, `musclePercent`, `fatMassLeftArmKg`, `fatMassRightArmKg` | `onBodyFat1` |
| 2 | `fatMassBodyKg`, `fatMassLeftLegKg`, `fatMassRightLegKg`, `muscleMassLeftArmKg`, `muscleMassRightArmKg` | `onBodyFat2` |
| 3 | `muscleMassBodyKg`, `muscleMassLeftLegKg`, `muscleMassRightLegKg`, `bodyWaterPercent`, `boneMassKg` | `onBodyFat3` |
| 4 | `bmrKcal`, `proteinPercent`, `visceralFat`, `subcutaneousFatPercent`, `bodyAgeYears` | `onBodyFat4` |
| 5 (dual only) | `fatMassKg`, `waterKg`, `proteinMassKg`, `muscleMassKg`, `weightWithoutKg` | `onBodyFat5`; unused fields omitted |
| 6 (dual only) | `skeletalMuscleKg`, `bodyScore`, `bmi`, `standardWeightKg`, `muscleControlKg`, `whr` | `onBodyFat6` |
| 7 (dual only) | `weightControlKg`, `bodyFatKgCon`, `fatMassLeftArmPercent`, `fatMassRightArmPercent` | `onBodyFat7`; first field unused |
| 8 (dual only) | `fatMassBodyPercent`, `fatMassLeftLegPercent`, `fatMassRightLegPercent`, `muscleMassLeftArmPercent`, `muscleMassRightArmPercent` | `onBodyFat8` |
| 9 (dual only) | `muscleMassBodyPercent`, `muscleMassLeftLegPercent`, `muscleMassRightLegPercent` | `onBodyFat9` |

Values are divided by 10 where the decompiled UI divides by 10; integer fields
(BMR, visceral fat, body score, body age) are left as integers. This is a
mapping from AILink's own UI code, not a vendor specification. Units are
therefore **hypothesis** until compared with AILink on hardware: BMI/percent
fields are percentages, kg fields are kilograms, BMR is kcal, body age is years.

Important: AILink also uses a proprietary Holtek SDK (`libBodyfat_SDK.so`,
`com.holtek.libHTBodyfat`) for some other body-fat products. The replacement
does not use it and does not calculate missing body composition for the GATT
families. The only local estimate is the LingYang broadcast estimate described
in section 10. If a GATT scale does not send state 9, the body-composition
section shows "not reported".

Range labels in the app (BMI, body fat, water, muscle, visceral fat, bone,
protein, BMR, body age, obesity index, body type) are derived from the
MIT-licensed `anxkhn/localscale` `ReferenceRanges.kt`: WHO Asian BMI cutoffs,
ACE/ACSM body-fat bands, typical BIA water/muscle/protein bands, and
Mifflin-St Jeor for the BMR comparison. They are presentation only and never
alter the stored measurement.

## 7. Stability, completion and deduplication

| Family | Live | Stable/complete | Save rule |
|---|---|---|---|
| CID 86 | type 1 | type 2 stable, type 10 complete | save last stable on type 10; a type 10 without a stable reading is ignored |
| CID 50/19/82/104 | state 1 | state 15 complete | save last weight on state 15; ignore if older than 30 s |
| Manual | current reading | user action | save as `manual`, clearly labelled |

Live weight packets during the 3-second stable hold are ignored, matching
AILink's `WeightScaleDevice.mStableStatus` behavior; a live packet after the
hold starts a new cycle. The UI waits 700 ms after a completion before saving,
so late body-composition frames in the same cycle can still be attached.
Body-composition frames that arrive when no reading is active are ignored; they
do not leak into the next measurement.

The repository also de-duplicates a completion that follows a stable/previous
save: same source protocol, weight within 0.02 kg and timestamp within 15 s is
one row. A manual row is upgraded to `complete` if a genuine completion arrives.

## 8. Handshake and encryption (not implemented)

`BleDevice` supports:

- A6 handshake commands `0x23`/`0x24` (`BleDevice.java:403-475`)
- optional A7 encryption via `AiLinkPwdUtil.mcuEncrypt` when the device is in
  AILink's license table (`BleDevice.java:267-298`, `AiLinkBleCheckUtil.java:310-360`)

The replacement does **not** copy AILink's license keys or encryption code.
Consequences:

- If the scale notifies unencrypted weights without a handshake, the app can
  decode them.
- If the scale requires a handshake or encrypted A7 payloads, weight
  notifications may be absent or unreadable. Diagnostics will show raw frames
  and an error; this is a known limitation.
- The optional "Send A6 version probe" button sends only the documented
  get-version command; it is not a handshake and may be ignored.

## 10. Hardware observation (2026-10-29, Galaxy M34)

A live scan on the connected phone found a device named `LYE` advertising:

```text
service:           0000f0a0-0000-1000-8000-00805f9b34fb
manufacturer data: 16 15 02 <6 bytes MAC redacted> 37 0c 24 59 16 63 8b e9 c3 ff ff
```

This matches the AILink **broadcast** scale family:

- `0000F0A0` is `BleConfig.UUID_SERVER_BROADCAST_AILINK`.
- The first three manufacturer bytes are CID/VID/PID (`0x16`/`0x15`/`0x02`).
  CID 22 is `BROADCAST_SCALE_LING_YANG_CID` in
  `aicare/net/modulebroadcastscale/BroadcastScale/BroadcastScaleBleConfig.java`.
- Byte 9 (`0x37`) equals the low byte of the sum of bytes 10-19, which matches
  `BroadcastWeightScaleDeviceData.onNotifyData` (type 65542): checksum byte at
  9, 10-byte payload at 10-19, then `AiLinkPwdUtil.decryptBroadcast`.
- The decrypted/unencrypted status byte would have to be 0 or 255. The raw
  payload's byte 1 is `0x24`, so the payload is not in plain text; AILink uses
  its native `decryptBroadcast`/`decryptLingYang` path.

GATT connection attempts to `LYE` consistently ended with
`GATT_CONN_TIMEOUT` / `HCI_ERR_HOST_TIMEOUT` (status 147). That is expected for
a broadcast-only scale; it is not a GATT peripheral. `BLE797P`, by contrast,
advertises service `0000F3C9` and is not the AILink device.

The replacement now implements the LingYang broadcast path:

- It slides a 20-byte window over the advertised manufacturer data, validates
  the checksum at byte 9, and decrypts CID `0x16` with the TEA variant used by
  `decryptLingYang` (initial sum `0xC6EF3720`, key words
  `31783163 306c6531 41493031 4c32796b`, sum decremented by `0x9E3779B9`).
- It parses status, stable bit, decimals, unit, weight, ADC and algorithm id
  from the first 8 plaintext bytes. The last two bytes are temperature and are
  not used.
- It validates status `{0x00, 0x01, 0x02, 0x03, 0xFF}`, weight `0..250 kg`, and
  ADC `{0, 0xFFFF} ∪ [1, 1000]` before accepting a frame. Only `5..250 kg` is
  saveable; an idle `0.00 kg` or sub-5 kg frame is shown live but never fed into
  the measurement session.
- `0xFF` marks the cycle complete and keeps the latest usable reading for the
  manual Save button; transient 0x00/0x01 frames update the live UI immediately.
- The Android scan path keeps scanning while a broadcast scale is selected; it
  never calls `connectGatt` for it.

Reference implementation and protocol notes:
`https://github.com/anxkhn/localscale` (MIT). The TEA constant is a local BLE
protocol constant recovered from Elink's published SDK; the app does not call
or bundle Elink's native library.

The user reported that a real weigh-in matched the scale display for weight.
Body composition, range labels and the other families still need a comparison;
keep the hardware-verification record honest. The idle sample decrypted on
2026-10-29 was:
`0c 24 59 16 63 8b e9 c3` → `81 00 04 00 00 00 00 11` (status 0, 2 decimals,
kg, 0.00 kg, ADC 0, algorithm 17).

For this broadcast family the app also estimates body composition locally from
weight + impedance using the open Jinghuawei/Aicare formulas (algorithm id 1)
ported from `anxkhn/localscale`. Height, sex and birth year are required from
the local profile. These values are stored with
`body_composition_estimated = true` and labelled **estimated**; they are not
received from the scale.
