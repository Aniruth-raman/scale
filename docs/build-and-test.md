### App data size

A debug APK extracts `app_flutter/flutter_assets/kernel_blob.bin` (~75 MB) and
`isolate_snapshot_data` (~11 MB) into the app's private data on first launch.
That explains ~90 MB of app data after debug testing; it is not measurements or
logs. The release build uses AOT and does not create those files. After removing
`app_flutter/` and reinstalling the release APK, the app's user data measured
**73 KB** (mostly the SQLite database).

## 6. Hardware test procedure

1. Unlock the phone, open **Scale**, tap **Connect scale**, grant
   Nearby devices permission.
2. Wake the scale, identify it by name/RSSI, connect. Open **Diagnostics** and
   confirm the GATT tree. The documented AILink service is `FFE0` with
   characteristics `FFE1/FFE2/FFE3`; the actual properties are recorded there.
3. Step on the scale at a known weight. Watch **Live measurement** and the
   packet log. A live reading must not be saved on its own. A stable/complete
   sequence should create one row.
4. Open the saved record and compare the weight with the scale display.
5. If body composition appears, compare each value with AILink for the same
   measurement. If it does not appear, record it as not transmitted for this
   scale.
6. Repeat in lb and st:lb if the scale supports unit changes.
7. Disconnect/reconnect and repeat; verify no duplicate rows.
8. Only after a successful comparison, open **Settings → Hardware verification**
   and record the test note. Update `docs/ble-protocol.md` with the actual
   payloads (redacted/synthetic excerpts only).

Known limitations to test explicitly:

- Handshake/AES-encrypted A7 devices are not supported. The app does not copy
  AILink license keys. If the scale requires encryption, weight decoding may
  fail even though the GATT connection succeeds.
- Background BLE is not implemented on either platform.
- The body-composition field mapping is from AILink UI code, not a vendor spec.
- The app does not calculate body composition; absent fields stay absent.

## 11. Signing and releases

Release builds are signed with a private key that is not in the repository.

| Item | Value |
|---|---|
| Keystore | `%USERPROFILE%\keys\scale-upload.jks` (outside the repo) |
| Alias | `upload` |
| Key | RSA 4096, PKCS12, 10,000 days |
| Subject | `CN=Aniruth Raman, O=Scale` |
| Certificate SHA-256 | `735D40C24A8282B309E51E2F24EAD51AF193B832F5EF400D38779C18FCECEF87` |
| Secrets file | `android/key.properties`, git-ignored; template `android/key.properties.example` |

`android/app/build.gradle.kts` reads `key.properties` for the `release` signing
config. When the file is absent the release build fails; it does not fall back
to the debug key, because an app published with a different key can never be
updated.

```powershell
flutter build apk --release
apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
```

Actual output:

```text
V2 Signer: certificate DN: CN=Aniruth Raman, O=Scale
V2 Signer: certificate SHA-256 digest: 735d40c24a8282b309e51e2f24ead51af193b832f5ef400d38779c18fcecef87
```

Installing that build over the debug-signed install fails, as it must:

```text
INSTALL_FAILED_UPDATE_INCOMPATIBLE: Existing package com.aniruth.scale signatures do not match newer version
```

So the debug-signed install has to be uninstalled once (which deletes its local
database) before a release-key build can be installed. Every later release
signed with the same key installs as a normal update.

Release steps:

1. Bump `version` in `pubspec.yaml` (`1.0.0+1` → `1.0.1+2`). Android refuses a
   `versionCode` that is not higher than the installed one.
2. `flutter build apk --release`
3. Name the asset and publish it:

```powershell
Copy-Item build\app\outputs\flutter-apk\app-release.apk Scale-1.0.1.apk
gh release create v1.0.1 Scale-1.0.1.apk --title "Scale 1.0.1" --notes "…"
```

Back up the keystore and its password (the password is in
`%USERPROFILE%\keys\scale-signing-credentials.txt`). Losing both means the app
can only continue under a new application id.

### Setting up a key from scratch

Only needed on a new machine, or if you deliberately start a new application id.
The commands are exactly what produced the key above.

1. Create the key outside the repository, with a generated password:

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\keys" | Out-Null
& "$env:JAVA_HOME\bin\keytool.exe" -genkeypair -v `
  -keystore "$env:USERPROFILE\keys\scale-upload.jks" `
  -storetype PKCS12 -keyalg RSA -keysize 4096 -validity 10000 `
  -alias upload `
  -storepass "<password>" -keypass "<password>" `
  -dname "CN=<your name>, O=Scale" -noprompt
```

PKCS12 requires the same store and key password. Store the password in a
password manager before continuing.

2. Create `android/key.properties` (git-ignored; use forward slashes):

```properties
storeFile=C:/Users/<you>/keys/scale-upload.jks
storePassword=<password>
keyPassword=<password>
keyAlias=upload
```

3. `android/app/build.gradle.kts` already contains the wiring; the parts that
matter are `import java.util.Properties`, loading `rootProject.file("key.properties")`,
a `signingConfigs.create("release")` block that fills in only when that file
exists, and `buildTypes.release { signingConfig = signingConfigs.getByName("release") }`.

4. Build and check the certificate:

```powershell
flutter build apk --release
apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
```

5. Confirm that the new key cannot install over a debug-signed build (see the
`INSTALL_FAILED_UPDATE_INCOMPATIBLE` output above). That failure is the proof
that the key is doing its job.

Restore instead of regenerate: copy the backed-up `.jks` back and recreate
`key.properties`. Generating a second key for the same application id would
strand every existing install.
