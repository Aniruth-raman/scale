# Privacy and platform notes

## 1. Design position

This is a local-first replacement for AILink. It has:

- no account or login
- no analytics, advertising, telemetry or crash reporting
- no cloud synchronization or automatic backup
- no application-initiated upload of measurement data
- no reuse of AILink endpoints, tokens, license keys or cloud code

The release build has **no `INTERNET` permission**. That is a platform-enforced
barrier, not only a policy promise. The debug build does include `INTERNET`
because the Flutter tooling needs it for the VM service; do not treat the debug
manifest as the privacy baseline.

## 2. Data stored

Local SQLite database (`scale.db`, app-private storage):

| Data | Purpose | Notes |
|---|---|---|
| Measurement ID | primary key | UUID v4 |
| Profile ID | household member | local UUID; no name leaves the device |
| Measured-at timestamp | history/trends | UTC epoch milliseconds |
| Weight in kg | normalized storage | display conversion happens once |
| Original value/unit/decimals | audit trail | e.g. `lb`, `jin`, `st:lb` |
| Status | complete vs manual | no transient rows |
| Source protocol | explain origin | e.g. `ailink.weight_scale.cid86` |
| Source device label | identify scale | device name only; **no MAC stored** |
| Body composition | transmitted or locally estimated | JSON map; absent fields omitted; `body_composition_estimated` marks estimates |
| Note | infant/manual context | optional |
| Profiles | name + optional height/sex/birth year | local only; used for range labels and estimates |
| Settings | units, active profile, verification note | local only |

Profile details and measurements stay in the app-private database. The app
sends them nowhere; CSV export and the shareable image are explicit user
actions through the system share sheet.

Diagnostics keep packet logs in memory only. Device identifiers are redacted
(MAC bytes and the displayed ID). Copying the log is a user action and copies
the redacted text to the clipboard.

## 3. Permissions

### Android

Supported range: Android 12 (API 31) and newer. This avoids the legacy
location requirement for BLE scanning.

Release merged manifest (`aapt2 dump permissions`):

```text
android.permission.BLUETOOTH_SCAN   (neverForLocation)
android.permission.BLUETOOTH_CONNECT
com.aniruth.scale.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION
```

`DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` is generated by AndroidX for
non-exported dynamic receivers; it is not a data-access permission.

No `INTERNET`, no location, no storage, no phone state, no health permissions.

The transitive RxAndroidBle dependency declares unqualified location
permissions. They are explicitly removed with manifest-merger `tools:node`
rules; verify this after any dependency change.

Runtime request: `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT` are requested by a
small Kotlin `MethodChannel`; denial produces a visible UI error and no scan is
started. The app never requests location permission.

The app starts a scan on launch and keeps it running while the app is in the
foreground so a broadcast scale can send every weigh-in without a manual
restart. There is no background scan, foreground service or scheduled scan.
Closing the app stops the scan; the scan mode is Balanced to limit battery use.

The **Turn on Bluetooth** button opens Android's own enable prompt (or the
Bluetooth settings screen if the prompt is unavailable). The app never enables
Bluetooth silently or requests location.

### iOS

`ios/Runner/Info.plist` contains:

- `NSBluetoothAlwaysUsageDescription`
- `NSBluetoothPeripheralUsageDescription` (legacy iOS)

No background BLE modes are enabled. iOS background behavior is not equivalent
to Android and has not been tested; see section 7.

## 4. Data movement

- **BLE** — the only network-like transport. It connects to the user-selected
  peripheral and receives notifications. No BLE data is forwarded to an
  application server.
- **CSV export** — reads the local database, writes a temporary CSV and opens
  the system share sheet. The app does not upload it. The chosen share target
  (mail, Drive, etc.) is outside the app and may transmit the file; this is the
  user's explicit action.
- **Shareable measurement image** — renders a PNG in memory, then hands it to
  the system share sheet. The app writes no permanent copy and uploads nothing.
  The chosen target receives the profile name, weight and body composition.
- **BLE listening** — a foreground scan starts on launch and stays active while
  the app is open, so a broadcast scale can send each weigh-in. It stops when
  the app is closed or the user taps stop; no background service is used.
- **Local database** — app-private SQLite; Android backup is disabled
  (`android:allowBackup="false"`), so the app does not participate in Android
  cloud backup by default.
- **Diagnostics** — in-memory; no automatic persistence; copy-to-clipboard is a
  user action.
- **No other network calls** exist in the codebase.

## 5. Verification performed

Commands and actual output are in `docs/build-and-test.md`. Summary:

- `aapt2 dump permissions build/app/outputs/flutter-apk/app-release.apk`
  shows only `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT` and the AndroidX dynamic
  receiver permission. No `INTERNET`.
- The release APK was installed on the connected SM-S938B (API 37);
  `dumpsys package` lists only `BLUETOOTH_CONNECT`, `BLUETOOTH_SCAN` and the
  dynamic receiver permission as requested permissions.
- The app launched without a crash. On the connected device the debug build
  auto-started a BLE scan at launch without user action and logcat showed
  nearby advertisements being received. The scale was asleep, so an automatic
  attach was not observed in that run; the attach path is covered by a
  controller test with a synthetic broadcast frame.
- The user exercised a live weigh-in, confirmed the weight matched the scale
  display, and exercised saving and the body-composition display. Permission
  denial, iOS and background behaviour were not tested on hardware.
- Runtime network capture on the finished build was **not** performed. The
  absence of `INTERNET` in the release manifest is strong static evidence, but
  this is not a claim of zero data leakage from the operating system, the share
  target or a debug build.

Do not claim "zero network" for the debug APK. The debug manifest deliberately
contains `INTERNET` for Flutter tooling.

## 6. Threat model and limits

- The database is protected by Android app sandboxing, not app-level
  encryption. A rooted device, a device backup with app data, or a malicious
  accessibility service could read it. Encryption at rest is not implemented.
- The app trusts the scale's notifications. A spoofed BLE peripheral could send
  crafted frames. The UI labels the protocol as candidate/unverified and the
  user selects the device; there is no pairing/bonding or authentication.
- Body-composition values are stored exactly as transmitted. The field mapping
  is reverse-engineered and not vendor-confirmed.
- Sharing a CSV exports the measurement data to the chosen app. The user
  controls that action.
- Release builds are signed with a private key kept outside the repository;
  see `docs/build-and-test.md` §11. The debug-signed APKs left in `dist/`
  predate that and cannot be updated by it. Only the template
  `android/key.properties.example` is committed; the keystore, the real
  `key.properties` and its password are not.
- Dependencies and their transitive manifests must be re-checked after every
  upgrade. The merged manifest is the source of truth.

## 7. iOS readiness

The BLE boundary (`lib/data/ble/ble_transport.dart`) is platform-independent;
the current implementation is Flutter Reactive BLE, which supports Android and
iOS. A future CoreBluetooth adapter can implement the same interface.

Not done on this Windows host:

- iOS build, signing, provisioning or App Store validation
- CoreBluetooth background behavior
- iOS permission/denial UX
- iOS share-sheet export

The Info.plist usage descriptions are present. Background BLE is intentionally
not enabled; document any future background mode and its App Store review
implications before adding it.
